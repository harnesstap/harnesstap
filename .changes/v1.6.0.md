## harnesstap v1.6.0 - October 22, 2026

### Added


  - Git dependencies can be pinned to a commit SHA (full or abbreviated), a tag or a branch, written `f8797fe`, `#main` or `ref:v1.2.0`; a semver constraint resolves to the highest matching tag. Install and apply check out exactly that ref instead of the default branch HEAD, record the resolved commit, and fail with the git error when the ref does not exist. `ht plugin doctor` accepts these constraints instead of reporting "Invalid version constraint", no longer asks a git URL for a marketplace, and warns when a git dependency is not pinned. `ht plugin add owner/repo#<ref>` imports a GitHub package at a ref, and `ht plugin update` keeps the pin. ([#500](https://github.com/harnesstap/harnesstap/issues/500))

### Fixed


  - `ht profile use` accepts a catalog profile's slug, its full ref `org/catalog/slug` (optionally `@version`), or its display name, and pulls the profile from the catalog when it is not installed locally. It used to fail with "Plugin not found" until you ran `ht profile pull`, and then accepted only the name the pull stored. With `--no-pull` or `--dry-run`, or when the catalog lookup or download fails, the error names the exact `ht profile pull` command. `ht plugin show`, `ht profile show`, and `ht plugin doctor` resolve a local plugin by the same slug, ref, or display name.

  - `ht profile use` installs a profile's marketplace dependencies in a home that has never registered their marketplace. `claude-plugins-official` and `karpathy-skills` resolve to their public git source, and a plugin that a marketplace lists by its own `url` or `github` source is cloned at the pinned version even when only HarnessTap (not the host) has the marketplace checkout.

  - Profile status no longer reports `.claude/rules` files as out of sync after you open a pulled catalog profile in the Library or run `ht plugin doctor` on it. Those read paths attached files from the package tree that the package manifest does not declare (for example a persona's `rules/`), so the profile stack changed without an apply and status listed files that were never written.

  - `ht profile use` no longer stops with "Invalid Version: ea10b213686c" when Claude Code already installed one of the profile's marketplace plugins and recorded a git sha as its version (for example `context7@claude-plugins-official`). The pin check treats such a version as not matching the pin and the apply goes on.

  - `ht migrate import` no longer drops plugin files silently. It names each skipped file with its path and reason: a `SKILL.md` without frontmatter, frontmatter that is not valid YAML (with line and column, for example an unquoted description containing a colon), or files under root `rules/`, `instructions/` or `mcp-servers/`, which are not part of the Agent Plugins layout (use `com.harnesstap/rules/`, `com.harnesstap/instructions/` or `mcp.json`). Imports print imported of discovered resources per type, and refuse such a package with exit 1 under `--strict`, the default when not interactive (`--no-strict` imports the rest). `ht plugin doctor` gains a `skipped-files` check that re-reads the installed package, so it no longer reports a plugin with dropped files as valid, and it prints the same per-type counts.

  - An MCP server shipped in a Claude plugin dependency (for example context7) is now written to ~/.claude.json on a global profile apply, and to other harnesses, instead of being dropped because its package-relative `.mcp.json` source looked like the Claude project MCP file.

  - `ht notifications` and the Desktop notification list keep newest first when two notifications are written in the same millisecond. They used to come back in a random order.

  - `ht profile show <slug>` works again for a profile that harnesstap 1.4.0 pulled without `--version`. That release recorded the version as `latest`, and every `name@latest` lookup failed with "Invalid version constraint: latest". A stored `latest` constraint now reads as any version everywhere, and a `name@version` lookup matches a stored version as written (`latest`, or `1.0` from `--version 1.0`) before reading it as a semver range. New pulls already record the package version.

  - The npm package and the Desktop sidecar report their release version (for example `1.4.0`) instead of a development string such as `1.4.0-dev+9dcdc1f`. `npm publish` rebuilt the CLI without the release flag. ([#501](https://github.com/harnesstap/harnesstap/issues/501))

  - Importing a plugin package that declares dependencies no longer marks the plugin as edited (`1.0.0*`). The dependencies come with the package, so the import is a clean working head at the package version, and `ht migrate export --plugin` exports it unchanged without a version bump. Edits made after the import still mark it edited. ([#499](https://github.com/harnesstap/harnesstap/issues/499))

  - `ht resource show` prints `none` for an empty Description or Path instead of a bare `:`, and the Updated time (also in `plugin show` and `catalog list`) is shown in local time instead of UTC. `environment show` and `environment list` print `none` for an empty description too. ([#453](https://github.com/harnesstap/harnesstap/issues/453))

  - Desktop resource detail shows the Path, Origin and delete-plan paths under your home folder with `~`, like the CLI and the hover cards. Copy path, Reveal and Open still use the full path. ([#452](https://github.com/harnesstap/harnesstap/issues/452))

  - A background marketplace catalog refresh that times out no longer logs "Couldn't reach". The cached catalog stays in use, the CLI prints nothing, and the Desktop agent log notes the timeout. A git timeout in an explicit refresh now says "Timed out after <n>s reaching <url>" instead of "Couldn't reach". ([#450](https://github.com/harnesstap/harnesstap/issues/450))

  - A `SKILL.md`, agent or rule file with invalid YAML frontmatter is reported the same way every time it is read. Before, the second read of the same text in one process (the desktop agent, or a second import or doctor run) silently parsed it as a file with no frontmatter, so plugin import and doctor named a different reason or none.

  - A failed `ht marketplace add` prints its "Couldn't reach" error once instead of twice. CLI errors no longer repeat a hint that says the same thing as the error. ([#451](https://github.com/harnesstap/harnesstap/issues/451))

  - `bun x harnesstap@latest` no longer fails with a page of node-gyp errors when the Node.js on `PATH` has no prebuilt `better-sqlite3`. The native SQLite module is now an optional dependency (Bun runs on `bun:sqlite`), so the install finishes, and an unsupported Node stops with one line that names Node 22.12 and, under Bun's runner, `bun x --bun harnesstap@latest`. When the module is missing on a supported Node, the CLI says how to reinstall instead of printing a stack. `npm install -g harnesstap` on Node 20 also installs and prints the version requirement instead of failing. ([#501](https://github.com/harnesstap/harnesstap/issues/501))

  - A plugin from a local Claude-format marketplace (`ht marketplace add <folder>`) is registered in `~/.claude/plugins/installed_plugins.json` and `enabledPlugins` when a profile is applied, so `profile status` reports it installed instead of missing. Claude loads its skills from the plugin, and Cursor gets it under `~/.cursor/plugins/local/`, the same way as a git-imported plugin. Plugins from remote marketplaces are unchanged. ([#449](https://github.com/harnesstap/harnesstap/issues/449))

  - Adding a plugin from a second marketplace that shares a name with one already in the library now stops with an error naming both, instead of silently replacing the first plugin's skills in the library and on disk. ([#448](https://github.com/harnesstap/harnesstap/issues/448))

  - Applying a profile to a project a second time no longer fails with "Invalid version constraint: main" when a git dependency is pinned to a branch, tag or full commit SHA. ([#500](https://github.com/harnesstap/harnesstap/issues/500))

  - A git dependency written with an empty constraint (`"constraint": ""`) is treated as unpinned, the same as `*`: apply installs the default branch HEAD instead of failing with "No local version of ... is installed", matching the `plugin doctor` warning. ([#500](https://github.com/harnesstap/harnesstap/issues/500))

  - The "Backup:" line after an apply removes files now prints the full path when HARNESSTAP_HOME is outside your home directory, instead of a broken `~//...` path. Home paths are matched on a directory boundary and, on Windows, with either separator and any drive-letter case.

  - A plugin fetched from git (a git dependency at apply, or `ht plugin add` of a git URL) is recorded as a clean copy at its package version instead of showing as edited (`1.0.0*`) in `ht plugin list`. ([#499](https://github.com/harnesstap/harnesstap/issues/499))

  - `ht migrate export` keeps each dependency's source: a marketplace dependency is written as `context7@claude-plugins-official` instead of `context7`, and a git dependency keeps its URL, so re-importing the export gives back the same dependencies. ([#499](https://github.com/harnesstap/harnesstap/issues/499))

  - In a fresh home, profiles that depend on public marketplaces other than `claude-plugins-official` (for example `reverse-engineering@claude-code-workflows`, `impeccable@impeccable`, `agentic-awesome-skills`) apply without `ht marketplace add`. The fix that apply prints, `ht resource sync plugin:<name>@<marketplace>`, now installs the dependency instead of checking 0 resources, and names the `ht marketplace add` command when the marketplace is unknown.

  - A marketplace dependency pinned to a version now resolves when the marketplace entry lists a commit instead of a version, or when the plugin repository has no `v<version>` tag: HarnessTap also tries the `<name>-v<version>` tag, the entry's pinned commit and the default branch, and keeps one only when its plugin.json declares the requested version (for example `chrome-devtools-mcp@claude-plugins-official` 1.11.0). A commit SHA given as a marketplace dependency version is reported as such, with how to pin a commit instead.

  - After `ht profile use` of a persona with marketplace dependencies, Desktop no longer shows the profile red with those plugins missing while `ht profile status` says in sync. A dependency that apply writes as files is not expected to be installed in Claude Code. `ht profile status` and `--check` now also report a profile plugin that Claude Code no longer has, the same way Desktop does.

  - `ht profile use` and `ht apply` no longer wait up to 2 minutes on a slow or unreachable marketplace remote when the pinned plugin is already cached. An exact version that is already in the package cache needs no network. Otherwise the stored catalog is used, and a stale one is refreshed in the background with the short timeout.

  - A plugin from a marketplace whose marketplace.json leaves out the version now installs at the version in its own plugin.json, as Claude Code does, instead of `0.0.0`.

  - A profile pinning a marketplace plugin to a version the marketplace has moved past now installs the commit that declared that version (or says which version is available) instead of caching the current copy under the pinned version, and an MCP-only plugin that declares no version, such as playwright@claude-plugins-official, no longer fails resource sync with "plugin tree is empty". A dependency with no version constraint on an entry that lists a commit or no version (such as `llm-council-plugin@llm-council`) installs that commit at the version its plugin.json declares instead of failing on 0.0.0.

  - `ht revert` of the first apply of a plugin now removes the plugin cache that apply installed under `~/.claude/plugins/cache`. The install runs before the apply takes its snapshot, so the snapshot counted every cache file as already there and the revert left hundreds of files behind (420 for staff-engineer, 5155 for agentic). The snapshot now records the files HarnessTap just wrote as absent before the apply. A revert still removes only files whose hash matches what HarnessTap wrote, keeps and warns about a file you changed or added, backs up what it removes, and puts back a file an earlier apply already owned.

  - A profile's dependencies on marketplaces it declares in `com.harnesstap/claude.toml` now resolve in a home without the `claude` binary: HarnessTap registers each missing declared marketplace (GitHub repo, git URL or local directory) itself on apply and on `ht resource sync`, and never changes one that is already registered.

  - A stalled git remote no longer hangs `ht profile use` and other commands. Every git clone, fetch and ls-remote now stops after 60 seconds, and git itself aborts a transfer that stays under 1000 bytes per second for 30 seconds. The `claude plugin` calls that clone marketplaces get the same stall detection and a 10 minute limit. The error names the repository (without credentials), for example `git ls-remote timed out after 60s for https://github.com/owner/repo.git`. Set `HARNESSTAP_GIT_TIMEOUT_SECONDS` to change the limit, and `GIT_HTTP_LOW_SPEED_LIMIT` or `GIT_HTTP_LOW_SPEED_TIME` to change the stall detection. A timed-out call also closes its output pipes, so a leftover git child cannot keep the command waiting.

  - `ht profile use <profile> --dry-run` now plans the pinned marketplace plugin folders the way the real apply does: it counts the plugin files it would write, lists the user files it would keep, names the files a user file in the way keeps it from writing (same warning as the real run), and exits 1 in that case, instead of saying "Would write 2" and exiting 0.

  - Switching away from a profile whose plugins `claude plugin marketplace add` cloned now removes the `extraKnownMarketplaces` entries that call declared in `~/.claude/settings.json` (when no kept plugin needs them and you did not change them), so Claude Code does not clone the marketplaces again, and prints a "Kept" notice naming each marketplace clone it leaves behind, with its folder, its size and the `claude plugin marketplace remove` command. The clones belong to Claude Code and are never deleted.

  - The apply summary counts every file written into a plugin cache folder that did not exist yet, such as the folder of a new plugin version, instead of saying "Wrote 1" for a 5 file plugin. ([#577](https://github.com/harnesstap/harnesstap/issues/577))

  - The apply summary suggests running the command again with --force-remove only when it would remove at least one of the kept files. When every kept file is a plugin folder file HarnessTap did not write, a folder, or a file that was already there, it says HarnessTap never removes these, even with --force-remove.

  - A plugin whose `.mcp.json` lists its servers at the top level instead of under `mcpServers` (such as `playwright@claude-plugins-official`) now has those servers imported and written to Claude Code, Cursor and Codex, so `ht profile status --check` no longer reports it as not installed after `ht profile use`.

  - A plugin whose plugin.json lists its skills as an array of paths (such as `mattpocock-skills`, with skills nested under `skills/<group>/<skill>`) now has every listed skill imported and written to `.claude`, `.cursor` and `.agents` skills. As in Claude Code, a listed path adds to the plugin's `skills/` folder instead of replacing it, and may be a skill or a folder of skills; paths outside the plugin are ignored.

  - A marketplace plugin with a skill whose frontmatter has an unquoted `: ` in a value (such as `claude-mem`'s `mem-search` description) no longer imports as an empty plugin that `ht profile status --check` reports as not installed: HarnessTap reads such flat `key: value` lines as strings, as Claude Code does.

  - A switch or revert no longer removes or changes an `enabledPlugins` key of `~/.claude/settings.json` the user wrote. HarnessTap records the keys it adds and only takes those out on `ht profile use`, so a key you had stays, and a plugin you set to `false` stays `false` (HarnessTap's copy of it is then not enabled) instead of being flipped to `true`. A key a switch takes out is restored by `ht revert` and given back to HarnessTap. A revert no longer drops the key of a plugin you installed with Claude Code (it is not held back with HarnessTap's plugins), and a held-back plugin keeps whatever key the file has now.

  - `ht revert` restores images, fonts, and other files that are not UTF-8 text byte for byte. A revert that restored files removed by `ht profile use` (such as a plugin's PNG icons) wrote them back as garbled, larger text; the removal backups were intact but the restore decoded them as text. Snapshots now keep such files as bytes, and the restore of removal backups and the rollback of a failed resource delete never go through a string. Drift stashing leaves a modified file that is not UTF-8 text in place instead of stashing a lossy copy.

  - ht revert no longer stops with a raw EEXIST or ENOTDIR error when a file or folder of yours is where a removed file has to go. It skips those paths and names what is in the way, never removes it (also with --force-remove), and restores the rest. The dry run shows the same skips as the real run.

  - Switching away from a profile no longer keeps the `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>` files of its marketplace plugins as "not made by HarnessTap". HarnessTap now remembers the host plugin folders its own installs create, counts their files as its own when an apply finds them already in place, and removes the folders left empty when it removes those files (with the usual backup). Folders it did not create, such as a Claude Code install, are left alone.

  - When a profile depends on a marketplace plugin whose name another marketplace's plugin already holds (for example `dup@mktb` while `dup@mkta` is in the library), `ht profile use` now refuses it before installing it, so the refusal no longer leaves a `~/.claude/plugins/cache/mktb/dup` folder behind.

  - After ht revert, the plugin folders it restores are HarnessTap's again, so the next ht profile use removes them with their registrations instead of keeping them as yours. A plugin is restored whole or not at all: when ht revert keeps your own installed_plugins.json or known_marketplaces.json as it is, it also leaves out the plugins and marketplaces those files would have registered, their cache files and their enabledPlugins keys, and says so. ([#579](https://github.com/harnesstap/harnesstap/issues/579))

  - `ht resource sync plugin:<name>@<marketplace>` now exits 1 when the dependency cannot be installed (an unknown marketplace or a failed download), with or without `--check`, and prints the `ht marketplace add <git-url> --name <marketplace>` hint for an unknown marketplace even when no plugin declares the dependency yet.

  - `apply --explain` shows the branch, tag or commit a git dependency is pinned to (for example `main`) instead of `*`.

  - `ht revert` now leaves ownership consistent. After `use staff-engineer`, `use default`, `revert`, settings.json is no longer skipped as modified: the `enabledPlugins` and `extraKnownMarketplaces` keys the switch took out are put back key by key and every other key stays as it is, so the restored plugins are enabled again. A host plugin file a revert puts back byte for byte is HarnessTap's again, so the next refresh replaces or removes it through the normal safe removal instead of leaving a stale SKILL.md. A plugin whose files cannot all be put back (a file or folder of yours is in the way) is skipped whole, with its record in `installed_plugins.json` and its `enabledPlugins` key, instead of being half restored and registered.

  - `marketplace show` and `plugin search` show a plugin's plugin.json version when the marketplace entry lists none, and no longer show a commit sha as the version.

  - A plugin missing from a known marketplace fails with "Plugin X not found in marketplace M." instead of "its marketplace entry names no git source", and `resource sync plugin:X@M` exits 1 with that message even when no plugin declares it.

  - `ht revert` restores files a profile switch removed instead of failing with "File not found", and they are HarnessTap's again, so the next switch removes them instead of keeping them as "not made by HarnessTap".

  - Refreshing a plugin in `~/.claude/plugins/cache` no longer deletes the existing folder. Only unchanged files HarnessTap wrote are replaced or removed, each backed up first; files it did not write or that changed are kept (asked in a terminal, `--force-remove` otherwise), and only empty folders are removed.

  - `ht revert` puts files back with the mode they had, so restored scripts and hooks stay executable. After `ht profile use <name>` then `ht profile use default`, reverting wrote every removed file with the default mode (0644), which dropped the executable bit from hundreds of scripts. Files kept in the trash, files captured live in the snapshot (new snapshots record their mode), and older removal records without a mode (the trash file's mode is used) all get their mode back. Links are restored as links and no mode is applied to them.

  - Switching away from a profile removes the `extraKnownMarketplaces` entries HarnessTap added to Claude Code's settings.json, so Claude Code no longer clones those marketplaces again on its next start. An entry you wrote or changed stays, a backup is kept, and `ht revert` puts the entries back.

  - Plugins that ship symlinks (such as `AGENTS.md -> CLAUDE.md` or a link to a folder) no longer abort `ht profile use`. Links are copied as links with their target unchanged, so a relative link keeps pointing at its sibling, links an earlier version made absolute are repaired, and cleanup never follows a link into another folder.

  - Files you add or edit in a plugin folder under `~/.claude/plugins/cache` are no longer deleted when you refresh, update, or switch profiles. HarnessTap now only treats files it wrote there as its own. When `--force-remove` replaces your files, it says which ones and backs them up, and `ht revert <id>` puts them back. Restoring never overwrites a file that changed since the backup unless you pass `--force-remove` again.

  - When a marketplace changes a plugin without bumping its version, `ht plugin update` now refreshes HarnessTap's cached copy of that version, so the next `ht profile use` or `ht apply` brings the new files into `~/.claude/plugins/cache`. Before, the old content stayed.

  - Test runs reset the host plugin refresh notices (kept, replaced, blocked and added files, and the force-replace flag) after every test, so a randomized full run no longer prints the counts of an earlier test's refresh in a later test.

  - `claude plugin install <plugin>@<marketplace>` now works from a marketplace HarnessTap registers with Claude Code. The marketplace's plugin entries used `../../cache/...` paths that Claude Code rejects; they are now `./plugins/<name>` paths, and each marketplace folder holds those trees as hard links to the plugin folders HarnessTap already keeps (copies where links are not possible). A file you changed or added there stays when the plugin leaves.

  - After `ht plugin update` moves a marketplace plugin to a new version, the next apply now writes that version into its own folder under `~/.claude/plugins/cache` and points Claude at it, instead of staying on the old version. Switching to another profile later removes the files HarnessTap wrote in the new folder, so it is no longer left behind.

  - After `ht plugin update`, a marketplace plugin's skills are no longer stored twice, so `ht apply` and `ht profile use` stop warning that a skill is "declared by p and p". The update now reuses the copy the last apply stored, and drops a second copy an earlier update left behind.

  - When `claude` is not on your PATH, a marketplace HarnessTap registers for Claude Code (for example `ecc` and `llm-council`) now names the same repository in `known_marketplaces.json` and in settings.json `extraKnownMarketplaces`. They used to differ, so Claude Code ignored the marketplace ("added but ignored") and listed its plugins as failed to load.

  - Switching away from a profile now removes the `extraKnownMarketplaces` entries HarnessTap added to Claude Code's settings.json even after Claude Code rewrote the file with its own key order (for example after `claude plugin install`). Only the marketplace of a plugin you installed stays, so Claude Code no longer clones the other marketplaces (thousands of files) again.

  - Switching away from a profile removes the `extraKnownMarketplaces` entries HarnessTap added to Claude Code's settings.json also when the switch writes settings.json itself, for example because the profile manages `hooks`. Before, those entries stayed behind (such as `claude-plugins-official` after `ht profile use default`) and Claude Code cloned the marketplaces again. Entries you wrote, and those of marketplaces the new profile declares, stay.

  - The notice about files kept in a `~/.claude/plugins/cache` folder now says which ones the plugin does not have (`--force-remove` would remove those, not replace them), shows once per change instead of on every `ht profile use` or `ht apply`, and the kept files are listed under `kept_plugin_files` in `--format json` output.

  - Files HarnessTap adds to a `~/.claude/plugins/cache` folder that already existed (for example one Claude installed) now count as HarnessTap's, so switching profiles removes them (with a backup) instead of keeping them as "not made by HarnessTap". The files that were there before stay yours and are kept.

  - The marketplace folders HarnessTap registers with Claude Code now live in `~/.claude/plugins/marketplaces/`, where Claude Code accepts them, so `claude plugin marketplace update` no longer fails with "corrupted installLocation" (an update replaces the folder with a clone, which HarnessTap then leaves alone). When a marketplace folder stays because you installed a plugin from it with Claude Code, its `marketplace.json` now lists only the plugins still installed, so installing one no longer fails with "Source path does not exist".

  - Removing a link that a plugin shipped (for example AGENTS.md pointing to CLAUDE.md, or a link to a folder) now removes the link itself on Node.js. Before, the link stayed on disk while the summary said it was removed, and each --force-remove run backed it up again. A plugin cache backup now always gets an id that ht revert takes, even when a removal fails midway.

  - `--force-remove` no longer deletes files or folders you added to a Claude Code plugin folder (`~/.claude/plugins/cache/...`). It now replaces only files HarnessTap wrote that you changed since; files HarnessTap did not write are always kept, and the notice says so instead of claiming the plugin no longer has them.

  - A folder or file of yours in the way of a plugin file no longer stops the rest of the plugin from being written. The command names the blocked paths and exits non-zero. ht revert says what is in the way, also in a dry run, and with --force-remove backs up a file HarnessTap wrote that is in the way, instead of failing with EEXIST.

  - The apply summary now counts new plugin files written to a plugin cache folder, next to the ones it replaced or removed. Before, a file new in the plugin was left out of "Wrote N".

  - `ht profile status` now compares each `~/.claude/plugins/cache` folder with the plugin itself, so it reports plugin files that are missing or out of date instead of saying in sync, and lists the files there that you changed or that HarnessTap did not write (apply keeps those).

  - `ht revert` puts links back as links. It used to restore a link to a file as a copy of that file, and leave out a link to a folder. When something else is at the path now, revert leaves it and says so.

  - Plugins a profile installs from a remote marketplace are now registered with Claude Code as real plugins (marketplace, installed_plugins.json and enabledPlugins, merged key by key) instead of copied in as standalone skills, so their hooks, commands, agents and MCP servers (with CLAUDE_PLUGIN_ROOT) work. Switching profiles removes only the registrations and plugin folders HarnessTap added, with backups, and keeps your own plugins and settings. No claude binary is needed. Codex and Cursor still get the standalone files.

  - When a git dependency is not fetched yet, `ht apply --dry-run` (and `--explain`) now says to run the apply without `--dry-run` to fetch it, instead of suggesting `ht plugin create`. The interactive recovery can also fetch it.

  - `ht revert <id>` for files that `--force-remove` replaced in the host plugin cache now puts them back without `--force-remove` when each file still holds what HarnessTap wrote, instead of keeping them as changed since the backup and restoring nothing.

  - `ht plugin add <name>@<marketplace> --to <plugin>` now checks that the marketplace lists the plugin. It exits 1 with "Plugin <name> not found in marketplace <marketplace>." instead of adding a dependency that cannot install.

  - `ht resource sync plugin:<name>@<marketplace>` for a plugin that the marketplace lists but no plugin depends on now exits 1. It says to add it with `ht plugin add <name>@<marketplace> --to <plugin>` instead of reporting "Checked 0 resources".

  - Switching profiles no longer stops with "has N unsaved changes" because of files in a plugin cache folder (`~/.claude/plugins/cache/...`). Those files belong to the plugin, not to the profile. Apply still keeps your own files there and lists them.

  - `ht plugin add <name>@<marketplace> --to <plugin>` now exits 1 with "Marketplace <marketplace> is not configured." and an `ht marketplace add <git-url> --name <marketplace>` hint when no registered, well-known, host or library declared marketplace has that name, instead of adding a dependency that cannot install.

  - A successful `ht apply` with a git dependency no longer prints "Plugin pin <url> is not installed locally" and "has no resolved version" afterwards. Apply now records the version the git fetch imported, and the version check no longer compares a branch, tag or commit constraint with the plugin manifest version.

  - After a profile switch or a plugin version bump, the files HarnessTap wrote into the old plugin cache folder (`~/.claude/plugins/cache/...`) are now removed, including the plugin's own `CLAUDE.md` and links such as `AGENTS.md`. Each is removed only while it still matches what HarnessTap wrote (for a link, its target), with a backup, and folders left empty go too. Files you changed or added stay and changed ones are listed. Links an install writes are now recorded with the apply.

  - When a plugin version bump or a profile switch leaves an old plugin cache folder behind, apply now lists the files of yours it keeps there (for example notes you added) instead of keeping them silently. They stay even with `--force-remove`, because HarnessTap never wrote them.

  - Claude Code marketplaces HarnessTap registers for a profile now have Claude Code auto-update turned off. When Claude Code still changes one (for example with `claude plugin marketplace update`) or a file in it, `ht profile status` lists it as kept, changed by Claude Code, instead of reporting the profile in sync or as unsaved changes, and apply or a profile switch keeps the entry with a warning instead of overwriting it or deleting the file it is in.

  - Replacing a file HarnessTap wrote with a link to a file outside your home no longer makes every apply and profile switch fail with "Refusing to materialize path outside root via symlink". The link is kept as your change and listed, HarnessTap never writes through it, and `--force-remove` replaces or removes the link itself (never its target) with a backup. A file under a folder that links outside your home is kept and reported instead of failing the apply halfway.

  - Re-applying a profile with a git plugin dependency that ships only a root `plugin.json` no longer replaces `.claude-plugin/plugin.json` in `~/.claude/plugins/cache/...` on every run and makes a new backup each time. The refresh of the plugin folder now leaves the files the apply wrote to the apply, so a second apply reports everything up to date.

  - A plugin you install with Claude Code from a marketplace HarnessTap registered (for example `claude plugin install name@marketplace` after `claude plugin marketplace update`) is now yours: switching profiles keeps its installed_plugins.json record, its enabledPlugins entry, its cache folder and the marketplace entry it comes from, with a warning that names the `claude plugin uninstall` command, instead of deleting them. Applying the profile again leaves that install alone too.

  - Removing a big plugin set (for example `ht profile use default` after a persona with thousands of downloaded plugin files) no longer copies every file into the undo database and the trash. Files HarnessTap wrote and nobody changed are moved into the trash, the undo row keeps no copy of their bytes, and `ht revert` reads them back from the trash. Files you edited, forced removals and links keep a full copy as before, and trash folders that hold the only copy of an undo are never pruned.

  - The apply summary now counts the files a plugin cache folder refresh replaced or removed, so it no longer says "Wrote 0, removed 0" or "Everything is up to date" next to "Backed up and replaced ...". The backup notice says "removed" for files the plugin no longer has, and the summary line starts with a capital letter when nothing was written.

  - An apply or profile switch that backs up removed files now prints the backup folder once ("Removed N files. Backup: ..."), instead of repeating a second "Backup:" line after the summary.

  - Applying a profile no longer fails with "plugin tree is empty" and a useless `resource sync` hint when your own Claude Code install record for one of its plugins (such as code-review@claude-plugins-official) points at a folder that holds no plugin. HarnessTap now looks past that folder for a real copy, leaves your record and folder alone, and switching away keeps them.

  - Switching profiles now takes the `enabledPlugins` entries HarnessTap added to an existing `~/.claude/settings.json` back out even when you have no `installed_plugins.json` of your own. Before, the entries stayed after the switch while `status --check` said everything was in sync. Your own `enabledPlugins` entries are left as they are.

  - The kept files hint now says to run the same command again with --force-remove, instead of always suggesting "ht apply --force-remove". When --force-remove was already used, it no longer suggests it again; it says HarnessTap never removes those files. The removal notice also names the files --force-remove removed only because of the flag (files you changed or HarnessTap did not create).

  - A switch or apply with --force-remove no longer stops with "EISDIR: illegal operation on a directory" (after removing some files) when you replaced a file HarnessTap wrote with a folder of your own. The folder is kept and listed, even with --force-remove, and the other removals go ahead.

  - Checking whether a file on disk is one HarnessTap wrote now reads it in small chunks instead of loading it whole, so large files no longer spike memory. The hashes are unchanged.

  - `ht apply <profile> --project` no longer stops on a hidden-Unicode character inside a third-party plugin's program file (for example a bidi control in a regex in a bundled `.cjs` script) in the Claude plugin cache. Findings in those js, ts, py and shell files are warnings; skills, commands, agents, hooks.json and MCP config are still blocked.

  - `ht apply --ignore-plugin-versions` no longer fails with "No local version of X is installed" for a dependency pinned to `*`, `latest` or a version range that is not installed yet. Only exact pins skip the host install now, since they are the only ones HarnessTap can resolve without it.

  - Switching profiles no longer reads every tracked plugin file into memory and into the undo snapshot. Files the switch removes are kept by their own removal backups, so a switch away from a large persona stays small and `ht revert` still restores them.

  - A link that a profile switch removes now sits in the undo trash as a link, and is put back as a link, instead of being kept as a text file holding its target.

  - `ht status --check` no longer reports image and other binary plugin files as modified right after `ht apply --project`.

  - A file kept in a plugin cache folder is no longer listed twice after `ht apply` or `ht profile use`, once in the kept list and again in the plugin folder notice. The kept count still includes it.

  - Applying again now counts every kept file in a plugin folder, including the ones an earlier apply already listed, and points to `ht profile status` for the full list, so the count matches status.

  - Switching to a profile that removes thousands of plugin files is much faster: HarnessTap no longer re-reads its plugin folder records and re-scans the plugin folder after every single removed file.
