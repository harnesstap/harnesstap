`rust-anything map --write .`. This file is the plan and the claims.

## Record and replay

Cases live in `app-cases/` (trycmd files). Every run goes through
`run-sandboxed.sh`: a fresh temp HOME per run, network calls refused, telemetry
off, no color. Workload and error-path inputs are generated by
`app-inputs/make-inputs.py` into `app-inputs/cases.jsonl`.

```sh
HT_RELEASE=1 bun run build        # the original, with a fixed version string
git checkout src/generated/scenarios.ts
rust-anything app record . --name ht --timeout 30 --inputs rust/app-inputs/cases.jsonl \
  --normalize timestamps --normalize uuids -- bash rust/run-sandboxed.sh node dist/bin.js
rust-anything app replay .                                     # the original
HT_RELEASE=1 cargo build --manifest-path rust/app/Cargo.toml   # bakes 1.6.3 like the original
rust-anything app replay . --build "bash rust/run-sandboxed.sh rust/app/target/debug/ht"
```

Always replay a Rust build through `run-sandboxed.sh`. `app front-door` and
`app wire` replay the binary directly, so run them with `HOME` set to a
throwaway folder.

The front door bakes the version at build time (`app/build.rs`), like tsup
bakes `__HT_VERSION__`. Build it with `HT_RELEASE=1` before a replay, or the
`--version` cases print the dev build string instead of `1.6.3`.

## Wave 1: core engine

Models first, then harness writers (`src/platforms/`), resolve, package-cache,
apm and lock, snapshots and revert.

`rust/models-rs` is a plain crate on top of `db-rs`, like `db-rs` itself: every
function takes a database handle, so it cannot go through `record`.
`models-rs/tests/make-fixtures.ts` runs the original under bun with a pinned
clock (`setSystemTime`), one scenario per model on a fresh database, and records
every call's result or error plus a dump of every table afterwards. The Rust
test replays the same calls with a step clock and creation-ordered ids, then
compares results, errors and tables with ids renamed in order of appearance.

Read-through note: the original memoizes some reads while a status computation
runs (`computationSlot`, `inStatusComputation`). The Rust ports always take the
uncached path, which returns the same rows; the cache comes with the status
port. Some original queries have no `ORDER BY` (for example
`findImportedSnapshotOwnersByFile`), so their order follows the primary key
index, which is why the fixture ids sort in creation order like real ULIDs.

## Open questions

1. `example-229-migrate` writes `harnesstap-state.tar.gz`, whose bytes change on
   every run (gzip and tar timestamps). The case keeps its stdout and exit code
   but no longer compares the archive. Compare the archive's content instead?
2. Network calls to a refused port print `Request timed out after 30000ms (3
   attempts)` within about a second. The port must reproduce that text (ADR-003)
   unless the original is fixed first.
3. Rust CI (build, clippy, replay) is not added: no workflow change without
   approval.
4. rust-anything 3.3.0 loops forever in `with_local_imports` (`src/gate.rs`) for any
   unit whose imports form a cycle through `../` paths: resolved paths are not
   normalized, so `a/../b/../a/...` keeps growing. `record`, `gate` and `map` on
   such units (`src/constants/`, and anything reaching `src/models` or `src/db`)
   need a build with one line added: canonicalize the resolved path. Until the
   fix is upstream, use that patched build for those units. Recording TS units
   also needs `--node-arg=--experimental-transform-types`, because
   `src/services/cli-errors.ts` uses parameter properties that strip-only mode
   rejects.

## Out of scope

The Desktop web UI (`apps/desktop/src/`), dev tooling in `scripts/` and
`apps/desktop/scripts/`, and the Tauri shell, which is already Rust.
